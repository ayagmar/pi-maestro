## Program invariants

All plans must preserve these rules:

1. No new runtime or development dependencies.
2. No release, version, tag, package publication, or changelog work.
3. The orchestrator must create the complete seven-plan board before driving; executors use normal repository tools inside their isolated task sessions and must not recursively invoke Maestro.
4. A failed, canceled, rejected, or cost-capped attempt must not modify the integration tree.
5. `approved` must identify a reviewed, integrated, verified artifact; manual acceptance must be visibly different.
6. Routine progress stays mechanical and token-free. Wake the strong orchestrator only for a decision or completion.
7. Expose only three LLM tools after migration: `maestro_plan`, `maestro_update`, and `maestro_drive`.
8. Keep human slash commands and dashboard recovery controls unless a plan explicitly changes them.
9. Never make an empty changed-file list mean “commit every dirty file.”
10. Test deletion cannot be used to make verification green.
11. Repository-controlled project config must not silently introduce executable verification commands.
12. Bounded model-facing diffs are presentation only; approval identity comes from complete Git objects.
13. Context savings must never omit success criteria, open blockers, or failed verification evidence.
14. Timeline/status features derive from existing evidence and add no analytics database or model wakeups.

## Findings considered and rejected

- Add a separate tool for inspect, steer, abort, handoff, pause, or status: rejected because these are drive control actions and would bloat the model schema.
- Build a run-level integration worktree immediately: deferred. Always-isolated task worktrees, Git-derived attribution, serialized integration, and write-set scheduling are simpler. Reconsider only if measured conflicts remain high.
- Add `readPaths`, risk matrices, and extensive planning metadata: rejected for now. A required bounded `writePaths` field gives the scheduler the needed conflict signal without bloating every task.
- Automatically retry arbitrary failures with a stronger model: rejected. Routing must be based on structured failure kind and repeated-cause evidence.
- Full event sourcing or a database: rejected as disproportionate; one persisted current decision is enough.
- General plugin framework/policy DSL: rejected as bloat. Trusted verification profiles cover the proven extension point.
- Predictive AI cost/success simulation: rejected. Plan simulation reports mechanics only.
- Immediate async board-lock rewrite: deferred until contention is measured after the higher-impact correctness work.
- Separate analytics storage or chart dashboard: rejected for now; compact accounting derives from existing attempts.
- New model-facing simulator/status/verification tools: rejected; keep all additions inside the existing three-tool or human-command surfaces.
